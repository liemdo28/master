# Phase 5H — component audit

Before designing `GovernedOrchestrationService`, every existing component that could
plausibly implement workflow/DAG/orchestration/approval/resumable-job behavior was
inspected and classified.

| Component | Location | What it actually is | Classification | Why |
|---|---|---|---|---|
| Task Runtime | `server/src/task-runtime/{engine,store,types}.ts` | Single-task state machine (`TaskStatus` + explicit `ALLOWED_TRANSITIONS` map), coding-oriented, `parentTaskId` gives a tree not a graph — no multi-dependency DAG, no Controlled-Actions binding. | **KEEP** (unmodified) | Phase 5H does not touch it. Its explicit-transition-map pattern is the architectural precedent Phase 5H's `ActionPlan`/`ActionPlanStep` status machines follow, but the schema itself is not reused — it has no concept of multiple dependencies per node. |
| Controlled Actions (Phase 5F) | `server/src/personal-os/actions/{service,store,types,policy}.ts` | `ActionProposal` → `ActionApproval` → `ActionExecution` → `ActionEvidence`/`ActionCompensation`, DB-constraint-enforced idempotency (`UNIQUE INDEX` on `idempotencyKey`), exact proposal/payload-hash/target binding. `ActionProposal` **already has a `sourcePlanId` field**, unused until now — clearly anticipated forward-compatibility with a planning layer. | **KEEP, reuse as the only execution surface** | This is exactly the canonical "propose → approve → execute" contract Phase 5H must delegate to. Phase 5H creates `ActionProposal`s (setting `sourcePlanId`) through the existing `ControlledActionsService`; it never talks to a connector directly and never writes to `action_proposals`/`action_approvals`/`action_executions` itself. |
| Governance engine (Phase 5G) | `server/src/personal-os/actions/governance/{engine,risk,budget,kill-switch,audit,store}.ts` | `ActionPolicyEngine.evaluate({proposal, approval, stage, actor, context})` → deterministic `PolicyDecision` (ALLOW / DENY / REQUIRE_APPROVAL / REQUIRE_STRONG_APPROVAL / BLOCK_KILL_SWITCH / BLOCK_BUDGET / BLOCK_CONTEXT), with a reproducible `decisionHash`. Deterministic `RiskEvaluator`, `BudgetManager`, `KillSwitchService`, `GovernanceAuditService` all called from inside `evaluate()`. | **KEEP, reuse as the only policy authority** | Phase 5H calls `policyEngine.evaluate(...)` at every Controlled-Action step boundary and persists the returned decision (id/hash/reasons) — it never reimplements risk/budget/kill-switch logic. |
| `GMAIL_SEND_DRAFT` action type | `types.ts`, `service.ts:641-642`, `governance/risk.ts` | A **registered but hard-blocked** type: `service.ts` throws `'GMAIL_SEND_DRAFT is documented but not implemented until draft creation is proven'` on any execution attempt; `risk.ts` forces it to `R4` (max risk) and marks it irreversible. | **IGNORE (never referenced by Phase 5H)** | Confirms Gmail SEND is already structurally unreachable, independent of Phase 5H. Phase 5H's step-type validator explicitly rejects any action type outside the 3 allowed ones (see §5), so this can never be selected even if someone tried. |
| Daily Operating Loop "plan" | `server/src/personal-os/operating/plan.ts` | `buildDailyPlan(...)` — a pure, read-only function that summarizes a day's brief into a `DailyPlan` (focus blocks, priorities). No execution, no steps, no dependencies, no approval semantics. | **IGNORE (different domain, name collision only)** | Shares the English word "plan" with Phase 5H's `ActionPlan` but is architecturally unrelated (a read-only daily-agenda view, not an executable action DAG). Documented here explicitly to prevent confusion — Phase 5H introduces no changes to `operating/plan.ts` or `DailyPlan`. |
| `coo-v4` durable workflow engine | `server/src/coo-v4/{durable-workflow,coo-orchestrator,types}.ts`, mounted at `/api/coo-v4` in `index.ts:308` (comment: "COO V4: Autonomous 24-Domain Engine") | A **separate, pre-existing, currently-mounted** SQLite-backed workflow engine (own DB at `.local-agent-global/coo-v4/workflows.db`, entirely independent of `personal-os.db`) with `workflows`/`workflow_steps`/`workflow_signals` tables: linear step-index ordering (no multi-dependency DAG), checkpoint/resume, and a signal mechanism for pause/approval-wait. **It has zero references to `ActionPolicyEngine`, `ActionProposal`, or any Phase 5G/5F governance primitive anywhere in its source.** | **IGNORE — explicitly not adapted, extended, or routed through** | This is the single most important finding of this audit. It already implements durable, resumable, signal-based step execution — architecturally the closest existing analog to what Phase 5H needs — but it was built with no governance binding at all, predates Phase 5F/5G entirely, and lives in a separate database. Adapting it would mean either (a) retrofitting the full Controlled-Actions/ActionPolicyEngine contract onto a system never designed for it — more work and more risk than building fresh on `personal-os.db`, which already has every governance primitive Phase 5H needs — or (b) leaving a governance gap. Phase 5H's `GovernedOrchestrationService` is architecturally independent of `coo-v4` and never imports from or calls into it. This is disclosed rather than silently ignored because `/api/coo-v4` remains live and unrelated to this phase's safety guarantees; it is out of scope for Phase 5H to modify or gate. |
| Agentic Coding engine | `server/src/coding/{workflow,impact-graph,engine-registry}.ts` | `impact-graph.ts` is a **file/symbol dependency graph** for static-analysis impact scoring of a single coding task — not a task/step orchestration DAG. `workflow.ts` is the single-task plan→apply→validate→review pipeline for one coding task, already fully governed by the frozen Coding Engine (explicitly off-limits per every prior phase's constraints). | **KEEP, unmodified, not reused** | Different problem domain (code-change impact analysis vs. multi-step external-action orchestration). The frozen Coding Engine boundary from Phase 5D onward is respected — Phase 5H does not touch `server/src/coding/`. |
| Project Registry / graph-db | `server/src/project-registry/*`, `server/src/graph/graph-db.ts` | Ownership/dependency graphs for *projects and code entities*, not action steps. `graph-db.ts`'s "DAG" matches are about ownership-graph traversal (SPOF detection), unrelated to workflow execution. | **IGNORE** | Different data model entirely; Phase 5H's step-dependency DAG is a new, small, in-plan concept scoped to `action_plan_dependencies`, not a reuse of the ownership graph. |
| GStack / multi-intent-splitter | `server/src/gstack/{gstack-orchestrator,multi-intent-splitter}.ts` | NLP intent routing for WhatsApp-driven work-order creation (splits a natural-language message into multiple intents, routes each to a handler). No persistent plan/step/approval state. | **IGNORE** | Pre-Phase-5, unrelated request-routing layer; not a plan executor. |

## Conclusions

- **No second Task Runtime, no second Controlled Actions engine, no second policy
  engine, and no second Personal OS database are created.** `GovernedOrchestrationService`
  is a new, additive layer on top of `personal-os.db` (schema v8 → v9) that creates
  `ActionProposal`s through the existing `ControlledActionsService` and evaluates them
  through the existing `ActionPolicyEngine` — it owns none of that logic itself.
- The one genuinely comparable prior-art system (`coo-v4`'s durable workflow engine) is
  deliberately **not** adapted, because doing so would either require retrofitting
  governance onto ungoverned legacy code or silently inheriting its governance gap —
  both worse than building fresh on the already-governed `personal-os.db` substrate.
- The only reused architectural *pattern* (not code) is Task Runtime's explicit
  `ALLOWED_TRANSITIONS` map, applied to `ActionPlan`/`ActionPlanStep` status machines
  to prevent silent state-skipping.
