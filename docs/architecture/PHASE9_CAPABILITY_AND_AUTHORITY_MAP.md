## Section 4 — Authority graph (Controlled Action path, both direct and orchestration-originated)

1. **Inbound caller** — `personal-os/actions/router.ts:33-52` (direct) or `orchestration/service.ts:442-476` (orchestration-originated). VERIFIED present both ways.
2. **Authentication** — dual mount, `requireRemoteAuth`/`requireTaskRuntimeAuth` (`index.ts:242,259`), preceded by rate-limit + IP guard. **Caveat**: `requireRemoteAuth` short-circuits entirely if `cfg.require_auth` is false (config-dependent open-bridge possibility, not a code defect); `requireTaskRuntimeAuth` compares the API key with `===` (not constant-time) — both worth the record, neither a live exploit today.
3. **Intent/request classification** — N/A for structured direct calls; for orchestration, `step.type === 'CONTROLLED_ACTION'` validated against a closed allowlist at both plan-creation and execution time (defense-in-depth, `orchestration/service.ts:79-92,432-438`).
4. **Project/tenant resolution** — `service.ts:129,752-754`; cross-project step targeting is a hard validation failure in orchestration (`service.ts:190-191`).
5. **Proposal/planning** — `propose()` computes risk/preview/hash/expiry, records policy decision + evidence + compensation row, all inside one DB transaction.
6. **Policy** — evaluated independently at proposal, approval, AND execution — three separate `evaluate()` calls, not cached/reused.
7. **Risk** — computed fresh inside every `evaluate()` call, never cached beyond the immutable `riskClass` set at creation.
8. **Budget** — 3-stage lifecycle (increment-on-proposal, increment-on-approval, atomic reserve-on-execution); **fail-closed on missing budget** — only 3 of 7 ActionTypes have a seeded budget, so the other 4 can be proposed but structurally can never reach `APPROVED`.
9. **Kill switch** — checked inside every policy evaluation, plus orchestration adds a standalone extra re-check before touching a step — orchestration is at least as strict as direct API callers, never less.
10. **Approval** — single approval surface (`POST /actions/:id/approve`); orchestration never self-approves except through the (disconnected — see below) delegation path.
11. **Execution** — re-derives policy/risk/budget/kill-switch fresh via `prepareExecution()`, never trusts a stale/cached authorization.
12. **Evidence** — recorded at every transition, comprehensively.
13. **Reconciliation — the one stage that is declared in the type system but has no implementation.** `RECONCILIATION_REQUIRED` (orchestration-step-level, `orchestration/types.ts:59,65,73,197`) and `RECOVERY_REQUIRED` (Controlled-Action-proposal-level, `actions/types.ts:13`) are both valid state-machine targets with zero code paths that ever set them — confirmed by direct grep in two independent passes. This is the single most significant structural gap in the entire authority graph: not a bypass, but an unimplemented safety stage.

**Delegation is architecturally wired into `GovernedOrchestrationService` but disconnected from every live production caller** — independently re-verified in this pass via direct grep of every `new GovernedOrchestrationService(...)` call site: `jarvis-gateway/services.ts:23` (the live Gateway singleton), `orchestration/router.ts:11` (the live HTTP router), and `orchestration/cli.ts:17` all construct it with **zero arguments**. Only test files and the delegation module's own acceptance/evaluation scripts (`delegation/phase5i-acceptance.ts:36`, `delegation/delegation-evaluation.ts:61`) pass a `delegation` argument. `delegation/router.ts`'s own live HTTP surface constructs a bare `DelegationService()` that builds its own internal `ControlledActionService`, not the orchestration singleton — so even the delegation router's live surface never reaches orchestration's `advance()` loop with delegation wired. **Practical effect: delegated auto-authorization is not reachable from any current production HTTP entrypoint.**

## Section 13 — Recovery/SelfHeal, incorporating the post-Phase-8 incident

What SelfHeal observes: ~9-11 named services (PM2/HTTP/internal-type checks). What it can attempt: `pm2 restart <name>` for PM2-type services only, capped at `MAX_AUTO_RESTART=2`, then escalates to a CEO alert. What it cannot attempt (deliberately, tested): kill any process, restart HTTP/internal-type services, touch DB migrations/deployments/financial ops. Intentional-stop semantics live in `runtime-preflight/validator.ts`'s `INTENTIONALLY_STOPPED` set (3 services) — but this is a **separate, not-reconciled list** from `self-healing-monitor.ts`'s own `SERVICES_TO_MONITOR`, which still actively health-checks `mi-ceo-observer` even though it's intentionally-stopped for boot purposes — a candidate documentation/reconciliation gap, not a live risk.

**Would automatically killing an orphan process holding a port require a new authority boundary? Yes — independently reasoned through and confirmed.** The `ActionType` enum has nothing OS-process-shaped. The Authority Control Plane registry already has a category built for exactly this (`effectClass: 'PROCESS_CONTROL'`) but every entry using it is `LEGACY_QUARANTINED` with `migrationTarget: 'future governed operations adapter'` — the registry's own language confirms this authority is not yet resolved into an exercisable capability. Every current process-terminating capability (Q, PM2 restart) is scoped to *named services the system manages*, not to *arbitrary processes identified by port ownership* — a categorically different, currently-nonexistent operation (`taskkill`/`process.kill(...,'SIGKILL')` grep found nothing beyond a liveness probe at `index.ts:627`). This is reinforced by a **deliberate, regression-locked** design decision, not an oversight: `operations/boot-preflight.ts`'s own docstring plus `operations/__tests__/phase7g-boot-preflight.test.ts:38` (independently re-verified in this pass) assert the fixture process holding a port remains alive after a preflight scan — a standing test that would fail the moment orphan-kill behavior was ever added.

## Section 14 — Proactive operations inventory

All governance-relevant proactive signals found (budget exhaustion, kill-switch state, policy drift, approval-waiting count, delegation expiry, legacy-quarantine count) classify as **OBSERVE** (pull-based `GET` computation) with one **ALERT-via-state-change** exception (delegation's policy-drift auto-pause, which mutates state as a read side effect but never grants anything, only narrows/blocks).
